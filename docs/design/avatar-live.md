# 数字人直播间 (第 16 格)

老板 2026-09-08: "第16个格我要放一个 AI 虚拟数字人直播"。

## 一句话

**没有重新选型。** 它和第 9 格「数字人」是同一套零件的两种用法 —— 通话是人对着它
说、它答; 直播是把写好的话术循环播出去。渲染、音色、形象、令牌、租户隔离、计费回报
全是现成的, 新写的只有**编排 + 推流**。

| 环节 | 用的什么 | 新写的? |
|---|---|---|
| 口型/人像 | SoulX-FlashHead-1_3B (L20 上已跑着) | 否 |
| 语音/音色克隆 | SoulX-Podcast-1.7B, 7 个音色 | 否 |
| 形象库/背景 | `/avatar/config` `/persons` `/bg.png`, 已按租户隔离 | 否 |
| 大模型 (按名称生成话术) | 自家网关 `/v1/chat/completions` | 提示词 + 一个端点 |
| 知识库检索 | 自家 `/v1/embeddings` + `/v1/rerank` | **还没接** (等弹幕问答) |
| 令牌/租户 | 与通话同一把 `AVATAR_TOKEN_SECRET` | 否 |
| **编排 (话术循环)** | `docker/live/live_server.py` (agentsdance 仓) | **是** |
| **推流 (合成 → HLS)** | 同上, ffmpeg | **是** |
| **页面与代转** | `server/app/live.py` + `/live` | **是** |

> ⚠️ **算力侧 (`live_server.py`) 一次大模型都没调** —— 它收到的就是一个字符串数组。
> 生成话术在**应用侧** (`server/app/live.py` 的 `/api/live/generate`), 而且生成的
> 内容只填进输入框、不自动保存: 它会被数字人当众念出去, 得有人过一眼。
> 知识库检索那行是"零件在手边", 不是"已经接上了" —— 它要等弹幕问答。

## 为什么是实时 —— 以及我一开始为什么做错了

**现在的形态**: 数字人说的每一句都是当场生成的。

```
[驱动: 话术循环 / 以后接 LLM 与弹幕]
    └─ 保持 avatar 的 say 队列里有两句 ──> /ws 实时生成
                                              │ 一句一个 fMP4
                                              ▼
                          转码合成背景 ──> 2 秒切片 ──> 追加进 m3u8 ──> 观众
```

**第一版做成了"离线渲染 + 循环播放", 那是错的。** 记下来是因为错的理由很有代表性:

我实测出整条链路恰好 **1.00× 实时** (122 字 → 25.02s 视频, 耗时 25.08s), 由此推出
"边生成边播永远攒不出缓冲, 一抖动就断流"。这个推论**把收支平衡当成了做不到**:
1× 的意思是生成多快、观众就消耗多快, 本来就不需要缓冲增长。

同日复测, 只要保持队列里有两句:

| | |
|---|---|
| 连续 70 秒 / 10 句 | 句间空隙 **最大 0.000 秒, 平均 0.000 秒** |
| 队列被抽空 (avatar 回 idle) | **0 次** |
| 首帧 | 3.57 秒 (TTS 预热, 只在开播时付一次) |

老板一句"我要的是实时数字人啊, 你这种渲染后再播放不是实时"点破的。
(参考 LiveTalking 的验收判据: `inferfps` 与 `finalfps` 都要 ≥25 —— 人家也是把 1×
当**及格线**在跑, 不是当天花板。)

**代价**: 直播开着就占掉 avatar 三路通话槽位里的一路。这是实时的价钱, 没有绕法 ——
预渲染省下的正是这个, 而省下它的结果就是"不实时"。

## 两处只有实跑才会撞见的坑

- **每句是独立编码的, 时间戳必须自己接上**。不处理的话每句开头都是一处 PTS 跳变,
  播放器要么要 `#EXT-X-DISCONTINUITY` (每句一次, 而每次不连续都可能让它清缓冲
  **黑一下**), 要么直接错乱。解法是转码时 `-output_ts_offset` 推上累计时长, 让整条
  时间轴天然连续, 播放列表里一个不连续标记都不打。
- **切片时长不能用 ffmpeg 那份 CSV 的 `end - start` 算**。实测: 带了
  `-output_ts_offset` 之后 CSV 里的 `start` 仍是 0 起算的相对值, 而 `end` 是加过
  偏移的绝对值 —— 相减等于把整个偏移算进时长, 播放列表里会冒出
  `#EXTINF:108287.400` 这种十万秒一片。正确算法是**相邻 end 之差**, 第一片对着本次
  偏移算。

## 并发口径 (按 3 路写)

`avatar` 服务的 `MAX_CALLS=3`, 两条产品线 (口袋专家 + AI Store) 共用。

- **直播开着就占 1 路** (它常驻连着 avatar 的 ws)。所以直播在播的时候, 通话的并发
  从 3 降到 2, 两条产品线共用。
- 这是**实时的必然代价**。想省掉它就只能回到放录像, 而那不是实时。
- 要不要把 MAX_CALLS 抬到 4: 抬之前必须实测四路并发下 `finalfps` 有没有掉到 25 以下
  (掉了就是所有人都卡, 而不是多服务一个人)。
- 页面上会显示 `starved` —— 队列被抽空的次数。不为零就是生成跟不上播出, 观众那边
  会卡, 而服务端一切正常。这个数必须露在人看得见的地方。

## 实测数字 (2026-09-08, L20)

| | |
|---|---|
| 生成速度 | ≈ 1.0× 实时; 保持队列两句时句间空隙 0.000 秒 |
| 开播延迟 | 首帧 3.57 秒 (TTS 预热), 只在开播时付一次 |
| 片段格式 | h264 512² 25fps + aac 16k 单声道, fMP4 |
| 播出 | 1280×720 25fps, 约 2 Mbps, HLS 2 秒切片 |
| 播出占用 | GPU: avatar 三路里的一路; CPU: 转码约 0.4 核 |
| 磁盘 | 只留滚动窗口的切片, 约 15 MB |

## 踩到并已修的坑

- **每句 say 是各自独立的 fMP4**, 用 `begin`/`end` 划界 (不是一条连续流)。所以按句
  存盘天然对齐, 但**不能**拿一个解码器从头吃到尾。
- **切片寿命 = 播放列表时长**。`delete_segments` 默认只在列表外多留 1 片, 于是切片
  在源站只活十几秒。客户端稍一缓冲、或中间隔着 CDN 慢一步, 手里的列表就有已经被删
  的片 → 404。症状是**播放器偶发卡顿而服务端一切正常**。修法 `hls_delete_threshold=20`
  (多留约 40 秒, 磁盘代价约 10 MB)。判据: 并行取全 200 而串行取丢片, 就是这个。
- **CSP 挡 blob:** —— hls.js 走 MediaSource, 少了 `media-src blob:` 就是"画面一帧不
  动"而只有浏览器控制台报错。数字人当年栽过一次, 已按同样方式按路径开口子并加了
  守护测试 (变异验过)。
- **HLS 同源代转而不是让浏览器直连 GPU 节点**: 直连要同时改 `connect-src` (等于给整
  页开跨源出口) 和 GPU 侧的 CORS。代价是视频字节流经应用机 (每观众约 2 Mbps),
  观众多起来换 CDN 回源 —— 换的是路由不是协议。守护测试钉住了"不该出现 connect-src"。

## 为什么没用社区那两个现成项目

调研时看的两个都是 lipku 的:

- **LiveTalking** (Apache-2.0, 9.4k star): 是渲染器, 而渲染器我们有。它的 README
  第 7 节声明"基于本项目开发并发布在B站/视频号/抖音的视频**需带上 LiveTalking 水印
  和标识**", 而作者自己在卖商用版 —— 卖给用户去带货的画面上挂别人家的标识, 这条就
  否掉了。真要用是发邮件谈商用授权, 不是当没看见。
  (它的 `streamout/` 分层思路值得抄: 出口是可替换的一层, 不焊死在渲染器里。我们照
  这个形状做的。它的双帧率判据也拿来用了: `inferfps` 与 `finalfps` 都要 ≥25。)
- **LiveStream** (同作者, 38 star): 是运营层 (话术循环 + 弹幕插播 + 知识库), 正好是
  我们要写的那部分。但仓库**没有 LICENSE 文件, README 里也一字未提许可** —— 没有许
  可证等于保留所有权利, 不能拿来部署, 更不能商用。它的功能清单可以当需求参考。

顺带: 那两个项目的默认模型链路 (wav2lip) 自身禁商用。我们这条线从模型到素材都在自己
手上, 唯一要确认的是 SoulX-FlashHead 的商用条款 —— 那是**存量**风险 (通话已经在用),
不是这一格新增的。

## 现在能做什么 / 还不能做什么

**能**: 官方直播间 7×24 播出。管理员在 `/live/console` 改话术、选形象音色、按名称
生成话术、渲染、开播停播; 所有登录用户在 `/live` 看。全站一套配置。

**还不能** (按优先级):

1. **用户自己的直播间** —— 现在**全站只有一套配置**(官方间), 控制台是管理员专用
   (老板 2026-09-08 定)。服务端本来是按租户分房间的, 要放开就是把"房间 = 官方间"
   改回"房间 = 登录态算出来的那一间", 外加一道容量口径 (每人一间意味着渲染要排队)。
2. **原先排在这里的"话术自动生成"已经做了** (2026-09-08): 控制台里填直播间名称,
   点"生成话术"→ 走自家网关出一版, **只填进输入框不保存**。审一道是刻意的 ——
   生成的话术会被数字人当众念出去, 带货场景说错一句功效/价格就是事故。
   提示词里明确禁止编造价格/优惠/库存/销量/功效/资质, 并且服务端会剥掉模型可能
   带上的编号与星号 (漏一个的代价是数字人念出"星号星号")。 —— 服务端的房间模型已经是按租户分的 (`/rooms/{tenant}`),
   缺的是页面上的话术管理与开播控制。
3. **推到抖音/视频号** —— ffmpeg 加一路 `-f flv` 输出即可, 技术上是小事。真正的门槛
   是: 用户的推流密钥 = 以他的名义开播的凭据, 我们代持要单独设计加密存储与随时撤销;
   以及平台对 AI 生成主播的标识要求与带货资质。
4. **弹幕互动** —— 拉评论 → 检索 → LLM → 打断插播。技术链路我们全有 (`stop` + `say`
   就是插播), 卡点在平台开放平台准入, 不在代码。
5. **待机动作** —— 现在靠"话术循环"让画面永远有内容。真正的待机 (不说话时的自然小
   动作) 还没做; 一旦有了实时插播就必须做, 否则插播间隙会定格。
