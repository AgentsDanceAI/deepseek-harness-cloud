# 工作区弹性伸缩指南

[English](workspace-scaling.md) | 简体中文

本文说明云工作区从单机容器迁移到弹性基础设施时需要保持的技术约束。具体生产
资源标识、网络地址、容量、价格和运行数据不属于公开架构文档，应在部署环境的私有
配置与运维系统中维护。

## 1. 设计目标

- 每个用户的工作区相互隔离；
- 工作区停止后，配置、历史和用户产物仍可恢复；
- 容量不足时明确拒绝新实例，不影响控制面和其他服务；
- 扩缩容后仍保持最小权限、私网访问和可观测性；
- 后端切换不改变上层工作区 API。

## 2. 状态与存储

每个用户有两类持久数据：

```text
dshwork-home-<id>  ->  /root
dshwork-ws-<id>    ->  /workspace
```

因此工作区不是无状态负载。调度到不同计算节点时，必须使用可跨节点挂载的存储，
或通过粘性调度保证实例回到持有数据的节点。任何后端实现还必须支持工作区停止时
读取用户产物；不能只依赖运行中容器的文件系统。

共享存储应为每个用户分配独立子目录，并在挂载前验证基础路径存在。应用层和存储层
都应执行隔离检查，避免仅依赖目录命名约定。

## 3. 计算后端选择

| 方案 | 适用场景 | 主要权衡 |
|---|---|---|
| 单机容器 | 规模较小、运维简单 | 容量和故障域受单机限制 |
| 弹性容器实例 | 工作区按需启动、空闲即停止 | 需要网络存储、镜像缓存和云 API 适配 |
| 无服务器 Kubernetes | 已采用 Kubernetes API 或需要生态集成 | 增加控制面和编排复杂度 |
| Kubernetes 节点池 | 持续负载较高、需要节点级调度 | 节点预热与容量规划成本更高 |
| 虚拟机伸缩组 | 需要完整主机控制 | 需要自建实例调度与粘性路由 |

选择前应以真实流量模型验证峰谷比、冷启动、存储性能和总成本。不要把并发上限、
单价或供应商配额写死在代码或公开文档中。

## 4. 后端接口边界

弹性后端应保持现有工作区生命周期语义：

1. 创建或恢复用户实例；
2. 查询实例状态与可访问地址；
3. 在真正可服务后报告就绪，而不是只依据基础设施的 `Running` 状态；
4. 停止或释放计算资源，同时保留持久数据；
5. 对超时、容量不足和挂载失败返回可诊断的错误。

`WORK_IMAGE_REF` 应使用不可变镜像引用。镜像版本、缓存版本和运行时版本需要在发布
检查中保持一致，避免实例静默回退到慢速拉取或运行不同版本。

## 5. 网络与安全边界

- 工作区端口只能从受信任的反向代理或控制面访问；
- TLS 终止层与工作区之间应走私网，并使用安全组或网络策略最小化来源范围；
- 不应把 `Host` 重写或容器内回环检查视为跨主机鉴权；
- 工作区可以执行用户代码，因此不得复用面向公网的宽松安全组；
- 云凭据只授予创建、查询和释放所需资源的权限，不授予进入用户容器执行命令的权限；
- 临时公网资源必须在成功和失败路径中都释放。

如果工作区需要出网安装依赖，应单独设计出口策略、域名控制和流量审计，不应因此
开放入站访问。

## 6. 容量与配额

静态并发上限不是唯一容量边界。实现需要同时检查：

- 可用内存和 CPU；
- 云账户或项目级实例配额；
- 公网地址、网卡、卷和挂载点配额；
- 共享存储容量与吞吐；
- 控制面 API 限流。

配额不可读取时应记录告警，并采用保守的容量策略。资源余量应保留给发布、缓存重建
和故障排查，不能让业务并发占满全部配额。

## 7. 冷启动与就绪验证

冷启动测试必须从 API 发起创建开始，到工作区端口真正返回有效响应结束。至少记录：

- 调度耗时；
- 镜像准备耗时；
- 容器启动耗时；
- 应用绑定端口耗时；
- 中位数、尾部延迟和失败率。

测试应覆盖镜像缓存命中与未命中、首次挂载、重复恢复和依赖安装。验收阈值由产品
SLO 定义，不应根据单次人工测试决定。

## 8. 镜像缓存

镜像缓存通常按镜像引用匹配。更新 `WORK_IMAGE_REF` 时，应由发布流程检查并重建对应
缓存；缓存不可用应产生明确告警。

部分云平台使用独立任务构建缓存，网络出口可能与业务实例不同。缓存构建需要的临时
网络资源必须显式创建、绑定并在 `finally` 路径释放。缓存状态应轮询到最终状态，并为
超时和失败提供可操作的诊断信息。

## 9. 存储验证

上线新后端前至少验证：

1. 写入 `/root` 和 `/workspace`；
2. 释放实例并重新创建同一用户；
3. 确认两处数据均恢复；
4. 使用另一个用户确认无法读取这些数据；
5. 验证基础路径缺失时能快速失败并报告原因；
6. 对代表性依赖安装或小文件负载执行性能测试。

## 10. 渐进式上线

推荐按以下顺序发布：

1. 在非生产环境完成生命周期、隔离和故障注入测试；
2. 使用不可变镜像和独立网络策略创建小规模试运行池；
3. 同时观察就绪延迟、失败率、配额余量、存储延迟和资源释放；
4. 按用户或租户逐步扩大流量；
5. 保留回退到原后端的配置开关；
6. 稳定后再调整空闲回收时间和并发上限。

生产环境的资源清单、成本模型、凭据策略和应急手册应存放在访问受控的运维文档中。
